- (direction) Spec-first as the way to work in the AI-assisted world: human decides what is true (the spec), AI writes the code. Source: brainstorm-intent.md
- (constraint) The corpus is TypeScript types (FSM + contracts + schemas), verified by tsc; one language for spec and generated code. Clojure/EDN/Malli excluded — contributes nothing here
- (capability) CAP-1 discover-and-record: human observes a state/contract in the live browser and records it into the corpus in the same session; AI assists via DOM/aria observation and FSM/contracts query
- (capability) CAP-2 three-concern test: run scenario, collect data, verify collected data as a pure function; corpus (snapshots, network events, DOM probes) is the deliverable, scripts are derived byproducts
- (capability) CAP-3 Gherkin as governance surface: test failure triggers a QE-written Gherkin scenario reviewed by PM/PO; the review outcome updates FSM/contracts (never an automatic write); failure is a human-adjudicated fork between spec drift and app bug
- (capability) CAP-4 graph as product artifact: the FSM/contracts graph answers (a) cognitive-load comparison between two starting states for the same user goal, (b) graph optimization proposing a new edge/shortcut, (c) standing invariants that critical tasks stay reachable from every important state at comparable cost
- (capability) CAP-5 repro script generation: from the FSM/contract model, emit a minimal script that reproduces a reported bug for a developer, without the framework as a runtime dependency
- (constraint) English strictly; use 'shared validator', never 'aspect'
- (constraint) FSM/contracts = SSOT, machine truth; Gherkin = human-readable input/query layer, never SSOT, never silently edited
- (constraint) Code failure is a trigger to update the spec, but the loop is NOT automatic — a human adjudicates spec-drift vs app-bug; the agent reports the discrepancy, never fixes the Gherkin silently
- (assumption) Browser automation layer assumed: Playwright over CDP against the live app, with the AI agent (opencode/goose + Playwright MCP) reading DOM/aria snapshots
- (assumption) Target app for the initial POC assumed to be Kraken Pro (live, read-only, authenticated CDP session) based on the session's domain-discovery material
- (question) Cognitive-load measurement: what is measurable from DOM/aria snapshots vs what needs human/UX judgment? Needs UX-method expertise before CAP-4(a) is implementable
- (question) Constitution.md is frozen history; its domain discovery (Kraken Pro FSM, contracts, granularity rules) is to be harvested — is harvesting part of this spec's scope or a separate later effort?
- (question) Corpus snapshot storage format: EDN was the constitution's choice, but the material is now TS — what format do recorded snapshots (DOM/aria, network events, DOM probes) take?
- (decision) Companion state-granularity.md: decision rules for what counts as a state (URL change, panel change, nested dialog) vs parameter vs contract — load-bearing for CAP-1 discover-and-record, multi-item catalog, too wide for one kernel line
- (decision) Adopt constitution.md as companion (path ../../../constitution.md): its Kraken Pro domain discovery is the seed corpus to harvest; downstream implementers need it. project-context.md is NOT adopted — declared obsolete

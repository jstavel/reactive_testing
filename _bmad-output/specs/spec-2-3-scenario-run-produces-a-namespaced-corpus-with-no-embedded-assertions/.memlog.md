- (direction) Why: Story 2.1 drives the browser, Story 2.2 collectors capture page data in-memory but write nothing. Story 2.3 closes the gap: it persists collector output into a namespaced, plain-data corpus with no assertions embedded, so collection and verification stay separate (FR-4).
- (constraint) Corpus files follow collectorType/run-id/stepIndex.ext; a run-manifest.json (run-id, timestamp, file list) is written per run (AD-15).
- (constraint) The run phase performs no verification — collection and verification are strictly separated; no assertions embedded in the run (FR-4).
- (constraint) The orchestrator assigns the run-id (UUID) and stepIndex; collectors never choose filenames (AD-15, epic-2-context).
- (constraint) Corpus is stored as plain data files, one format per file, never embedded in TypeScript — snapshots (corpus/snapshots), network (corpus/network), screenshots (corpus/screenshots), probes (corpus/probes) (AD-13, FR-4, consistency conventions).
- (constraint) Screenshots stored as file references (ScreenshotRef), not image bytes in corpus data (AD-13).
- (constraint) tsc --noEmit clean; TypeScript-only; English-only identifiers; import type for type-only imports (verbatimModuleSyntax).
- (constraint) The orchestrator is offline and deterministic — no AI calls during execution (AD-4); read-only v1 scope, no mutating contracts (NFR-3).
- (capability) CAP-1: A scenario run persists collector output into a namespaced corpus of plain-data files (collectorType/run-id/stepIndex.ext). Success: given a scenario run whose collectors return in-memory corpus data, when the run persists each item, then files are written under collectorType/run-id/stepIndex.ext with no assertions embedded.
- (capability) CAP-2: A run-manifest.json is written per run recording run-id, timestamp, and the file list. Success: given a completed run, when it finishes, then a run-manifest.json exists listing run-id, timestamp, and every corpus file written.
- (capability) CAP-3: The orchestrator assigns a unique run-id (UUID) and an incrementing stepIndex; collectors never choose filenames. Success: given a run, when corpus data is persisted, then each path derives its run-id/stepIndex solely from orchestrator-assigned values and no collector-invented name appears.
- (capability) CAP-4: The run performs no verification and embeds no assertions. Success: given a scenario run, when it executes, then no validator/assertion logic runs and the corpus files contain only captured plain data (FR-4).
- (decision) Story 2.3 is the storage/wiring layer over Story 2.2: it consumes in-memory collector output (not browser pages) and persists it; integration wiring is this story (Story 2.2 assumption).
- (decision) run-manifest.json is the per-run record: run-id (UUID), timestamp (ISO-8601), and the list of corpus file paths written (AD-15).
- (decision) Corpus root uses the fixed folders corpus/snapshots, corpus/network, corpus/screenshots, corpus/probes (architecture consistency conventions); stepIndex is the per-step ordinal within the run.
- (constraint) Non-goals: collector capture/return (Story 2.2); collector error isolation and partial-corpus writes (Story 2.4); validator execution and reporter output (Epic 3); Gherkin parsing (never, AD-9).
- (assumption) Story 2.2 collectors already return typed in-memory corpus data to the orchestrator; Story 2.3 persists that output rather than re-capturing the page.
- (assumption) The corpus output directory is writable and located under the project (architecture structural seed); the exact on-disk location and CI wiring are configured during implementation.

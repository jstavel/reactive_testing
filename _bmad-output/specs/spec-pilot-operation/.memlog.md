- (direction) Pilot goal is BOTH: (a) learn the project via a full review of what is already done, and (b) create new tests using the project — pilot is the act of onboarding + authoring new scenarios
- (direction) Onboarding docs: BOTH — use/validate the existing docs as the onboarding vehicle, and extend them where the pilot reveals gaps
- (direction) Feedback loop: Jan writes issues into a backlog as they appear; the backlog is reviewed together after one story completes
- (direction) Success criterion: a new user is able to extend tests in the project; Jan will attempt to cover a few new scenarios (exact number open for later discussion)
- (capability) CAP-1: A new operator can onboard by following the docs alone — set up prerequisites, record a corpus, and extend the test suite by authoring new scenarios. success: a first-time reader using only README.md + docs/* can go from zero to a recorded run and a new authored scenario without asking an expert.
- (capability) CAP-2: The pilot surfaces actionable refinement feedback — doc gaps and friction points recorded as backlog issues. success: every gap or friction hit during the pilot is captured as a backlog item with enough context for a later story to act on it, and the backlog is reviewed after one story completes.
- (capability) CAP-3: The onboarding docs are extended only where the pilot reveals gaps, so the next new user is better served. success: the doc gap each issue names is closed (doc edit or explicit won't-fix recorded) by the end of the epic.
- (constraint) The pilot uses the existing docs as the sole onboarding vehicle; Jan refrains from explaining anything the docs omit during the run so gaps become visible and recordable.
- (constraint) New tests authored in the pilot must follow framework conventions: Gherkin with a valid @plan:<PlanId> tag (smoke|regression|acceptance), contract/FSM entries in the model, and read-only scope (NFR-3).
- (constraint) Open retro items epic-3-item-7/8/10 and epic-4-item-5 stay open/waiting and are OUT of Epic 5 scope; they are implemented later when an opportunity arises.
- (constraint) Feedback is recorded to a backlog as issues appear; the backlog is reviewed together after one story completes, feeding the next story.
- (non-goal) Not building new framework capabilities unless a pilot gap makes one necessary.
- (non-goal) Not implementing the open retro items (epic-3 item-7/8/10, epic-4 item-5) — deferred to when an opportunity arises.
- (non-goal) Not a CI/CD or production rollout; the pilot is local and hands-on.
- (non-goal) Not FR-10/FR-11 (graph queries / reachability) — still deferred to v1.1.

topic: Story 2.2: Specialized collectors (snapshot, network, screenshot, probe) that receive the page from the orchestrator and capture page-derived data in their own format, conforming to schemas.ts corpus types (AD-5, AD-13)
updated: 2026-08-27T15:49
---

- (constraint) Each collector is page-in, corpus-data-out (AD-5); no collector writes its own files or chooses filenames in this story.
- (constraint) Produced data must conform to corpus types in schemas.ts (AD-13): SnapshotRecord, NetworkEvent, ProbeResult, ScreenshotRef — one format per file.
- (constraint) Corpus structure: corpus/snapshots/, corpus/network/, corpus/screenshots/, corpus/probes/. Collectors named collect-*.ts (collect-snapshot.ts, collect-network.ts, collect-screenshot.ts, collect-probe.ts).
- (constraint) Runtime data serialized as plain data; never embedded in TypeScript code; screenshots stored as file references (ScreenshotRef), not bytes.
- (constraint) No storage/writing (Story 2.3 owns run-manifest, run-id, stepIndex naming); collectors return captured data in-memory to the orchestrator in this story.
- (constraint) tsc --noEmit clean; TypeScript-only; English-only identifiers; import type for type-only imports (verbatimModuleSyntax).
- (capability) CAP-1: SnapshotCollector receives a live page, captures serialized DOM/aria as a SnapshotRecord and returns it in-memory. Success: given a loaded page, when snapshot collector runs, then it returns a SnapshotRecord with the page's serialized structure and capturedAt.
- (capability) CAP-2: NetworkCollector receives a live page, records HTTP request/response events observed during the step as NetworkEvent objects. Success: given a page performing requests, when network collector runs, then it returns NetworkEvent records with url/method/status/capturedAt.
- (capability) CAP-3: ScreenshotCollector receives a live page and captures a viewport screenshot, returning a ScreenshotRef (file reference + capturedAt). Success: given a loaded page, when screenshot collector runs, then it returns a ScreenshotRef pointing at a saved PNG.
- (capability) CAP-4: ProbeCollector receives a live page and one or more probe definitions, extracts each value via a DOM selector, and returns ProbeResult objects. Success: given a probe definition, when probe collector runs, then it returns ProbeResult with the extracted value and capturedAt.
- (capability) CAP-5: Each collector returns data conforming to its schemas.ts corpus type and can be invoked by the orchestrator with a Playwright Page. Success: given any collector, when invoked with a Page, then its return value validates against the matching schema.
- (constraint) Non-goals: no corpus writing/naming (Story 2.3); no run-manifest (Story 2.3); no error isolation (Story 2.4); no orchestrator changes; no validators (Epic 3); no Gherkin parsing (AD-9).
- (assumption) Collectors run one-per-call; the orchestrator invokes each collector separately after a step (integration wiring is Story 2.3).
- (decision) Collector contract: each collector is a function accepting a Playwright Page (and optional collector-specific options) returning its corpus type. Shared CollectorFn<T> type holds the common shape.
- (decision) ScreenshotCollector persists PNG bytes to a ScreenshotRef file path; but in-story it returns the ref and a temporary/local write path; storage policy deferred to Story 2.3.
- (decision) ProbeCollector accepts an array of probe definitions {name, selector} and returns ProbeResult[].
- (direction) Why: the orchestrator (Story 2.1) drives the browser but captures nothing. Dedicated collectors (snapshot, network, screenshot, probe) each capture one concern of page-derived evidence cleanly, so the run can store per-concern corpus data later (Story 2.3).

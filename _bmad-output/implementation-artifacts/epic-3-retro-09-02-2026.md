## Findings

### Aggregate view — spec-to-implementation reconciliation

**F1 — FR-6 offline re-validation is broken against real corpora: the pre-step snapshot filename collides**
- **Source:** `orchestrator/orchestrator.ts:276-279` writes the per-step pre snapshot with the constant stem `"pre"` → `snapshots/{runId}/pre.json`, overwriting the same file on every step; the manifest accumulates repeated identical `pre.json` entries (verified in `corpus/10fa96c0…/run-manifest.json`, `corpus/ed47e511…/run-manifest.json`). Meanwhile `validators/corpus-loader.ts:118-127` reads `snapshots/{runId}/{stepIndex}.pre.json` (e.g. `0.pre.json`), and `orchestrator/corpus.test.ts:96-106` asserts the convention is `0.pre.json`.
- **Live behavior check:** `runValidatorsOffline` over all four real recorded corpora (`_offline-check.ts` against `corpus/10fa96c0…`, `ed47e511…`, `47624bc6…`, `98fce638-bf55-4673-b099-b0d3c96e9031`) reports **every step** `[precondition] missing snapshot evidence` — no precondition can ever pass. Post-snapshot and probe predicates load, showing the drive is specifically the pre-step naming.
- **Verdict:** the writer (Story 2.7-era code, pre-epic) and the reader (this epic's Story 3.3) disagree on the pre-step file name. The unit tests pass because the loader tests hand-write `0.pre.json`/`1.pre.json` (loader's convention) — no test runs the real orchestrator write path back through the loader. FR-6's promise ("new rule without re-running the scenario") cannot be honored on any previously recorded corpus.
- **Disposition:** **fix now** (align the writer to the documented per-step convention or the loader to the writer, plus an orchestrator→loader integration test). — **LANDED 2026-09-02** (see Action Items): writer now emits `${stepIndex}.pre` (`orchestrator/orchestrator.ts`), and the round-trip regression guard `orchestrator/offline-roundtrip.test.ts` records through the real writer and re-reads through `loadCorpusSteps` — verified red against the old stem, green with the fix. `npm test` 179 pass. Historical corpora recorded before the fix keep the old `pre.json` layout and are regenerable.

**F2 — `blockedContractIds` (AD-18) is dead code: the promised consumer never shipped**
- **Source:** `validators/reachability.ts:13` computes it; Story 3.2's spec change log says "surfaced by the 3.4 reporter — not dead code (unlike retro F1's vestigial `action` field, it has a documented future consumer)". But Story 3.4's `reporter/failure-gherkin.ts` consumes only `ValidationResult + TestPlan` (imports at `failure-gherkin.ts:15`), and `reporter/adjudication.ts` likewise. `grep -r "blockedContractIds" --include=*.ts` finds no consumer outside its own test file (`validators/reachability.test.ts`).
- **Verdict:** the enumerated gap (a validator whose state no path reaches is flagged) is never reported; the claim this is "not dead code" is false today.
- **Disposition:** **defer** — either wire it into a reporter story or drop the claim; the pure computation + test is correct and reusable.

**F3 — Duplicated plan-walk logic: three implementations of stepIndex→contractId**
- **Source:** `orchestrator/orchestrator.ts` (`executeScenario` loop + `stepIndex` accumulator), `validators/corpus-loader.ts:85-113` (`planSteps` defensive re-implementation), and `orchestrator/orchestrator.ts` `planCollectors`/`validateProbeDependencies` each independently iterate `plan.scenarios[].steps[]`.
- **Verdict:** the mapping global is `List` step index for the loader is duplicated (and the loader's is defensive, the orchestrator's is not). A plan-shape change touches three sites; the loader's unit tests — the only proposer that chronologizes — never pin the orchestrator's index. This is the seam modicum of F1.
- **Disposition:** **defer** (fold into the F1 fix which must add the integration test).

### Diff-scope review / available-leads

- **Verdict:** This is expected staging for a POC (specs 3.4/3.5 show them as Reporter modules), but is worth recording so the next epic knows FR-6/7/8 are "shipped as libraries, wired to nothing" — not resumably lost.
- **Disposition:** **recorded / accept as-is**, surface the gap when the runner story lands.

### Commit attribution (process)

**F5 — the epic's own dev-loop commits bypass the branch policy; attribution breaks on the first three stories**
- The AGENTS.md policy ("never commit a story directly to main; each story lands as a single-commit PR from a `feat/story-<N>` branch") was added mid-epic (`b96e560`). Stories 3.1–3.3 were committed directly to main (`4de6d25`, `ea37b61`, `bec2d2c`) with no PR; 3.4–3.6 and later went through PRs #3/#4/#5.
- Git-evidence attribution: the subjects of 3.1–3.3 commits say "Story 3.1" (dot) but the story id is "3-1-validators-are-pure-functions-over-the-corpus", so `git_evidence.py` scored all dev commits with `stories: []` and only the merges for the PR-based stories count. Attribution for this epic therefore rests on merge branch names, not the author's subjects. This is a recurring variant of Epic-2's F4 (commit subjects must name the story id).
- **Disposition:** process note; fix "subject naming" in the working rule.

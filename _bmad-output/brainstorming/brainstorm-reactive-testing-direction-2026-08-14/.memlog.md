- (insight) User sees no benefit of Clojure/Malli vs TS-based specs for the spec store itself; Malli slightly better to read
- (insight) User is re-enabling Clojure skills deliberately; krakatoa (~/dev/krakatoa) is a Clojure/Rust project alongside
- (insight) Decision has two evaluative dimensions: technical fit AND personal skill-goal (re-enable Clojure), plus career goal (Kraken TS job)
- (insight) Substitute lens result: spec store is language-neutral — the SSOT does not decide the stack; so the decision lives somewhere else
- (insight) Real decision drivers surfaced: (a) re-enabling Clojure is a deliberate skill goal, (b) Kraken speaks TS (career), (c) krakatoa sibling project is Clojure/Rust
- (insight) Deadline: Kraken application THIS week; POC is the #1 POW (27 pts across 7 roles), 1-2 weeks to demo
- (insight) Kraken ad explicitly wants: Playwright, MCP integrations, building an automation framework, trading domain. QA role does not require Rust.
- (insight) User: 'Clojure does not bring anything extra into this project. The intent is to present spec-first testware.' Separation idea: krakatoa carries Clojure re-enablement, this POC carries the Kraken evidence.
- (idea) Demo moment 1: hook opencode, prompt 'you are at page History, simulate making order' vs 'you are at Home, simulate making order' — compare cognitive load; showcases state reuse
- (idea) Demo moment 2: hook opencode, prompt 'generate a simple JS script to simulate happy path from Home to History, filtered Withdrawals' — the emitter idea, generated script
- (decision) Decision: Clojure/EDN/Malli brings no benefit to THIS project. The spec layer is invisible machinery in the demo, not the spectacle. The polyglot-emitter core (ADR-2) is dead in its Clojure form.
- (insight) The real payoff: FSM + contracts + DOM/aria snapshots as a structured corpus enables DEEP QUERIES that ad-hoc tests cannot — e.g. measuring the cognitive load of user operations (how many state hops a task needs).
- (insight) Second payoff: from the FSM/contract model you can emit a minimal repro script for a developer fixing a bug — generated from the same spec data, no framework needed
- (insight) Shift-left intent (from Red Hat): the spec/ADR/FSM/contracts corpus is a LIVE part of development, not a document — it grows as you discover the app, edited alongside code
- (question) User doubts: 'It seems like over-engineered approach at first glance' — the full FSM/contracts/corpus architecture vs a 1-2 week POC with a deadline this week
- (decision) Decision: drop the week-deadline framing entirely — no time pressure. The project's real goal: adopt spec-first as THE way to work in the AI-assisted world. It's a way of working, not a portfolio deadline.
- (decision) The spine of the habit: discover-and-record. Live discovery of a state/contract in the browser, recorded into the corpus in the same session. Everything else (agent pickup, generation, queries, repro) hangs off it.
- (idea) Discover-and-record workflow: (1) write gherkin scenario manually or with AI, (2) decide if it warrants a new FSM state, (3) name the contract the scenario describes. User hopes AI assists all three.
- (insight) The step-2/step-3 judgment rules already exist in constitution.md (granularity table: URL change = state, same URL = parameter, dialog = nested state). The AI needs those rules plus the existing FSM visible at decision time.
- (insight) Corpus of snapshots + network events is the testing deliverable itself (snapshot-driven testing) — not the scripts. Scripts are derived.
- (insight) Reactive testing distilled: a test = three separated concerns — (1) run the scenario, (2) collect data, (3) verify the collected data. Verification is a pure function over collected data.
- (insight) Role of agent clarified: the agent is a coder — reads the spec and writes TS. User drives: (1) observe DOM/aria via agent to draft gherkin, (2) agent queries FSM/contracts by scenario to decide if a new state/contract is required.
- (decision) The material IS TypeScript types — they play the same role EDN/Malli schemas would: FSM + contracts + schemas as typed TS. One language for spec and emitted code; tsc verifies the spec itself compiles.
- (insight) User question: does the settled design comply with Model-Driven Testing? Likely answer: yes — FSM+contracts is the model, scenarios generated from it (MBT), model as SSOT with generated artifacts (MDD applied to testing).
- (insight) Deep motivation: the AI revolution. Coding will increasingly be AI's domain, not humans'. This project is the user's adaptation strategy — spec-first as the human's enduring contribution in a world where AI writes the code.
- (insight) Reverse lens considered: SSOT could be code itself (fully reversible) — but evolution tracking is harder because code blocks can't be separated the way scenarios can. Key benefit of scenario files: traceable and transparent.
- (insight) Closed the loop: code failure is a trigger to update the spec. Generated TS is a sensor — when it breaks against the live app, the scenario/FSM is out of date, and that failure lands back as a spec update. Shift-left: spec stays true because code watches it.
- (insight) NOT an automatic loop: the spec can be true and the APP can be buggy. Failure means EITHER spec drift OR app bug — the decision is human. The constitution's rule: agent reports the discrepancy, never silently fixes the gherkin.
- (insight) Gherkin is easier for a PM to read — a second reason for gherkin as spec layer. Workflow: test fails → QE writes a gherkin scenario → PM + PO review it together. Gherkin is the human-negotiation interface between QE and PM/PO.
- (decision) Confirmed the social/governance shape: FSM+contracts = SSOT (machine truth), Gherkin = human negotiation interface QE↔PM/PO, failure = trigger for human adjudication (spec drift vs app bug), never an automatic write.
- (idea) Cognitive-load query made precise: two scenarios lead to the SAME user goal (e.g. user wants to list his orders); the corpus has DOM/aria snapshots for both full paths; AI compares the difficulty of the task relative to the user's starting state.
- (insight) User hopes established UX methods exist for cognitive load (not a UX expert) and that AI/UX experts can read difficulty from DOM/aria. Open thread: what is measurable from the DOM vs not.
- (idea) Complaint-driven query: 'task is hard from History' → AI searches the FSM/contracts graph for alternative paths to the same goal, or proposes a shortcut (new contract) that shortens the journey — a recommendation, not a test.
- (decision) The complaint-driven query is GRAPH OPTIMIZATION: propose new paths (new edges/states) to be added to the FSM. The product improvement IS a new edge in the model. FSM becomes a product-design artifact, not just a test model.
- (idea) Global invariant over the graph: for a few user-critical tasks, AI verifies the task is reachable from EVERY important state with similar cognitive load. Consistency of access = a property the corpus checks, not a test.
- (decision) constitution.md stays frozen as historical design record — its domain discovery (Kraken Pro FSM, contracts, granularity rules, validation layers) will be harvested later. Fresh decision doc carries the new direction.
- (insight) Session synthesis: the idea is complete — spec-first in the AI era, TS types as the material, three-concern architecture, discover-and-record spine, Gherkin as human-negotiation surface, graph as product-design artifact (cognitive-load queries, proposed edges, standing invariants).

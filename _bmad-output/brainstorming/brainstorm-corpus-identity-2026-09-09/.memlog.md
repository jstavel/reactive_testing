- (technique) started How Might We
- (idea by user) CLI to query the corpus and to create/make/delete temporary links into the corpus (and into the corresponding network, probes, etc.) - like building a second brain
- (insight by user) Core use case: after running smoke tests and seeing failures, immediately work with the exact corpus produced by that run.
- (direction by coach) Optimize first for direct handoff from run-smoke to the exact corpus, not retrospective fuzzy search; the run itself knows the authoritative runId.
- (decision by user) NPM scripts are the operator-facing 'UX API' for corpus handoff (run + query scripts), not a bespoke CLI tool
- (idea by user) No cd in the corpus script - it should just print/resolve the corpus path; the user gets into the dir themselves
- (direction by coach) corpus UX = print the resolved canonical corpus path for the operator to reuse (cd, editor, report) - no side effects beyond printing
- (idea by user) The corpus link must wire the corresponding per-kind dirs (network/probes/snapshots/screenshots) - one run = a fan of kind paths, not a single dir, because corpus/ is kind-split
- (decision by user) Keep the 'lake' layout: kinds are siblings (cross-run queryability), the per-run manifest is the run-level index, and the @name links reassemble a run across kinds without collapsing the layout (no layout migration)
- (decision by user) Keep UUID as runId: opaque random ids impose lower cognitive load than human-readable datetimes, which invite parsing
- (decision by user) @last-fail disappears when a run passes; it only exists to point at the latest FAILING run
- (decision by user) MVP scope is only creating/removing symlink views during run; the broader second-brain query/index experience is a separate future RFE

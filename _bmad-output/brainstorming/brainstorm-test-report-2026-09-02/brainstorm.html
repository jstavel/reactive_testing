Test Run Report Design

A brainstorming keepsake — thinking recorded
reactive-testing · 2026-09-02 · partner mode · complete
00 — The Question

What information should a test report contain?

Not "what widgets do we add?" but the deeper question: what does a person need when they open a report — to know if things pass, to fix what breaks, and to trust the system that told them.

01 — Technique

First Principles Thinking Decomposition

Strip every assumption about what a "test report" looks like. Rebuild from the three irreducible user needs.

Need 01

Proof

Visual evidence that a step happened. Screenshots are the minimum — a sequence of screenshots per step is the atomic unit of proof.

Need 02

Debugging

When something fails, show exactly where and why. DOM snapshots, FSM state, contract assertions with actual-vs-expected — on demand, not by default.

Need 03

Trust

The report must not lie. A green bar with hidden failures is worse than no report at all. The structure must resist false confidence.

Insight — Robot Framework lineage

Robot Framework already solved this UX: green/red color coding, sequential steps, click to expand a screenshot at that moment. We inherit that proven pattern — but replace its keyword DSL with Gherkin.

Insight — FSM as differentiator

FSM state in the report resonates because the target audience thinks in architecture and framework terms. It's the differentiator from Robot Framework.

Decision — KISS

Single self-contained HTML file. Expandable details for QE expert depth. Error messages: start simple, iterate.

02 — Technique

Six Thinking Hats Parallel Lateral Thinking

Each hat forces a single perspective. The richness comes from the collision between them — especially the tension between black-hat fear and green-hat invention.

☾ Black Hat — Risks

  • Screenshot bloat inflates file size unboundedly
  • DOM snapshots make reports unreadable for non-QE
  • FSM state noise distracts from the actual failure
  • False green — all steps pass but user goal fails
  • Flakiness — acknowledged but out of scope
  • Stale Gherkin — spec drifts from implementation

◆ Green Hat — Ideas

  • Tags as filters — show only @critical failures
  • Copy-Gherkin button — report becomes seed for new tests
  • Severity gradient — not just pass/fail
  • Report as living spec — it proves itself on every run

☼ Yellow Hat — Value

  • Report as living specification — always current
  • Teaching tool for new team members
  • Gherkin text makes the report self-documenting
  • Progressive disclosure serves both quick-scan and deep-dive

○ White Hat — Facts

  • Robot Framework proved the UX: sequential, expandable, color-coded
  • Gherkin is already the source of truth for scenarios
  • FSM state is available from the framework at runtime
  • Contract assertions already produce actual vs expected

▲ Red Hat — Instinct

  • Excitement about the Gherkin request/answer framing
  • FSM state feels right — it's how we think
  • The single-HTML instinct is strong: keep it simple
  • Unease about screenshot bloat — needs mitigation

■ Blue Hat — Process

  • First Principles grounded the problem in user needs
  • Six Hats stress-tested the emerging design
  • MoSCoW now needed to scope v1
  • KISS instinct consistently pulled toward progressive disclosure

The Design in Layers

Layer 1 — Summary
Green/red bar at the very top. Pass count, fail count, total. Run metadata (environment, timestamp, duration).一眼で分かる — understood at a glance.
Layer 2 — Gherkin Tree
Feature → Scenario → Step. The same Gherkin text the team wrote, with a green/red dot per scenario. Collapsible. The spec is the report is the spec.
Layer 3 — Progressive Disclosure
Click to expand any step: screenshot, DOM snapshot (on failure), FSM state, contract assertions with actual-vs-expected, timing. Depth on demand, silence by default.
Layer 4 — Embedded Source
The Gherkin feature file embedded in the report itself. The report carries its own spec — no stale reference, no broken link. What ran is what you read.
06 — Synthesis

What We Learned

  • The report is a spec artifact that proves itself on every run. It doesn't just describe behaviour — it demonstrates it.
  • The Gherkin-as-request-answer framing is the core insight that unifies spec and report into one artifact.
  • KISS instinct consistently pulled design toward progressive disclosure: simple surface, rich depths.
  • FSM state is the differentiator from Robot Framework. It's the piece that makes the audience think "this is for us."
  • Tags and the copy-Gherkin button are small UX wins with outsized feel — deferred to v2 but already designed in spirit.
  • Black-hat risks (bloat, false confidence, stale specs) were all acknowledged and mitigated within the design — screenshot on demand, DOM only on failure, embedded Gherkin.
Final reflection

This session moved from "what goes in a report?" to "what is a report?" The answer: it's the second half of a conversation the Gherkin spec started. Everything else — screenshots, FSM, contracts — is just evidence for the answer.

"Gherkin scenario is the request, the report is the answer."
